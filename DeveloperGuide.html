Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows the components interacting for delete i/A0123456B.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Logic component

API : Logic.java

The add and delete sequence diagrams below show how parsed commands change a temporary model before the live model is updated.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Here are the other classes in Logic (omitted from the class diagram above) that are used for parsing a user command:

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • uses studentId as the domain identifier for Person duplicate checks. The JavaFX id label in PersonListCard.fxml is only the displayed list index, not the student's identifier.
  • stores group labels as Label objects inside each Person.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user's preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of labels in AddressBook, and each Person references values from that list. This lets AddressBook maintain one value object per unique label instead of each Person holding its own objects.

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • expects each stored Person JSON object to contain a valid studentId. There is currently no migration or default-value strategy for old data files missing this field.
  • stores group labels through JsonAdaptedLabel. Missing or null labels fields are treated as empty label sets for compatibility with older data files.
  • ignores legacy tags fields when loading older data files and omits them when saving.
  • reports loading failures as DataLoadingException, distinguishing unreadable files, invalid data, and duplicate Student IDs. See Loading student data at startup.
  • writes student data atomically and reports a data folder that cannot be created as DataStorageLocationException. See Saving before publishing changes.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Group labels

An optional group label is assigned when creating a student with add ... l/LABEL_NAME. Label validates the value, and ParserUtil#parseLabel trims command input before constructing it. JsonAdaptedLabel and JsonAdaptedPerson persist labels under each person's labels JSON field. EditCommand preserves existing labels, and PersonCard renders them in its FlowPane. Existing saved labels remain compatible, including records containing multiple labels.

Edit command

Format: edit i/STUDENT_ID [n/NAME] [e/EMAIL] [r/REMARK] [l/LABEL_NAME]... [dl/LABEL_NAME]...

EditCommandParser checks command structure and parses the Student ID and requested field changes. It collects repeated l/ and dl/ values into the EditPersonDescriptor. An empty l/ requests clearing all labels and is rejected if combined with another label change. An empty r/ becomes an empty remark.

EditCommand finds the student by Student ID in the complete address book, so a filtered view does not change the target. It builds a replacement Person, keeping fields that were not supplied. For labels, it copies the student's set, removes each dl/ label, then adds each l/ label. Matching is case-insensitive. Removing a missing label or adding one already present throws a CommandException, leaving the record unchanged. An empty l/ produces an empty label set. The command then replaces the student through Model#setPerson; LogicManager saves the pending model before publishing it to the live model.

Mark and unmark attendance

Command formats:

mark i/STUDENT_ID d/YYYY-MM-DD l/GROUP
unmark i/STUDENT_ID d/YYYY-MM-DD l/GROUP

The accepted inputs, examples, and feedback are documented under Recording attendance and Removing attendance in the User Guide.

Parsing and validation

AddressBookParser routes each command to MarkCommandParser or UnmarkCommandParser. Both tokenise i/, d/, and l/, accepting any parameter order and exactly one non-empty value for each. Their structure checks follow the same order: internal line breaks, unknown prefixes, preamble text, repeated prefixes, then missing or empty values. Repeated and missing/empty checks use i/, d/, l/ order. The general command parser rejects multiline input before command-specific parsing.

Both parsers reuse ParserUtil#parseStudentId, ParserUtil#parseDate, and ParserUtil#parseLabel, in that order. The date parser requires a valid calendar date in the strict YYYY-MM-DD format. The parsers then construct MarkCommand or UnmarkCommand with the validated values.

Matching and updating records

Both commands search Model#getAddressBook().getPersonList() by normalised Student ID, so a student hidden by the active filter can still be updated. A missing student throws CommandException before any change.

  • MarkCommand first finds a current group label using case-insensitive matching. It creates an AttendanceRecord(date, matchedGroup) and rejects an existing entry for that date and group. Otherwise, it adds the record to a copy of the student's attendance set.
  • UnmarkCommand searches the existing attendance set using AttendanceRecord#equals, which compares dates exactly and group names case-insensitively using Locale.ROOT. A missing record throws CommandException. Otherwise, it removes the matched record from a copy of the set. Current group membership is not required: EditCommand retains attendance when labels change, and historical records must remain removable. Success feedback uses the matched record's stored group spelling.

Each command constructs a replacement Person, retaining every other field, and calls Model#setPerson. Other attendance entries and the active filter remain unchanged. unmark removes the specified attendance entry; like other successful data changes, it can later be reversed by undo.

Saving and sequence diagrams

Both commands return true from Command#isModifyingData. LogicManager blocks them after a startup loading failure, executes them on a pending model, saves that model, and only then publishes it to the live model. Parsing, command, or save failures preserve the live records, filter, and previous saved file. The existing attendance JSON representation is reused; no storage format change is needed.

Adding student information

Command format: add n/NAME i/STUDENT_ID e/EMAIL [r/REMARK] [l/LABEL_NAME]. One optional group label can be assigned during add; Label defines its validation rules. The accepted values and exact error messages are documented in the User Guide.

Validation and identity

  • ArgumentTokenizer recognises supported prefixes at the start of arguments or after whitespace, including tabs.
  • AddCommandParser checks line breaks, unknown alphabetic prefixes, preamble text, repeated prefixes, missing mandatory fields, then empty mandatory fields. Errors are reported before parsing field values. Repeated/missing/empty checks follow n/, i/, e/ order; repeated r/ and l/ are checked after them.
  • ParserUtil trims values and converts invalid fields into ParseExceptions. Model constructors also validate, so records created by storage or other callers follow the same rules.
  • Name accepts 1–100 Unicode code points after trimming and collapsing repeated spaces, requires a letter, and permits Unicode letters/combining marks, spaces, apostrophes, hyphens, and periods. Case is preserved.
  • StudentId accepts nine ASCII alphanumeric characters and stores uppercase using Locale.ROOT. Person#isSamePerson compares this normalised ID, not the name or email.
  • Email enforces the supported ASCII format, local-part limit of 64, overall limit of 254, domain-label limits of 63, and a final label of 2–63 letters. Only the domain is lowercased using Locale.ROOT.
  • Remark accepts at most 4,000 Unicode code points; command parsing trims only surrounding whitespace. Empty or omitted remarks become empty strings. r/ can appear anywhere and does not consume later parameters.
  • Label accepts 1–60 Unicode code points and requires at least one letter or digit. It permits letters, combining marks, digits, spaces, hyphens, underscores, apostrophes, parentheses, and periods. Empty labels are rejected, omitted labels become an empty label set, and l/ can appear anywhere without consuming later parameters.

For example, add n/ Alex Tan i/a0123456b e/Alex@EXAMPLE.COM l/Tutorial 1 r/Quiz: 8/10 creates a student with name Alex Tan, ID A0123456B, email Alex@example.com, label Tutorial 1, and remark Quiz: 8/10. An alphabetic token such as x/value is rejected even inside a remark; 8/10 and URLs remain literal text. A duplicate ID rejects the complete command without merging any details or remarks.

Saving before publishing changes

The execution path is:

AddressBookParser → AddCommandParser → AddCommand
LogicManager → temporary ModelManager → JsonAddressBookStorage → live ModelManager
  1. Command#isModifyingData identifies commands that alter student records. add, edit, delete, mark, unmark, clear, and undo return true. Future modifying commands must override this method too. undo uses the separate snapshot transaction described in Undoing data changes.
  2. LogicManager copies the live records and current filter into a temporary ModelManager, then executes the command against that copy. Copying the filter preserves the active view if saving fails; edit identifies its target by Student ID from the full record list rather than by displayed index.
  3. JsonAddressBookStorage writes the proposed records to a temporary file in the destination directory. Files.move with ATOMIC_MOVE and REPLACE_EXISTING replaces the old file only after writing completes. There is no fallback overwrite when atomic replacement is unsupported. Temporary files are removed after failure.
  4. After saving succeeds, LogicManager publishes the proposed records and filter to the live model, then returns the success feedback. If saving fails, it returns Unable to save student data.; live records and the active filter are unchanged, and the previous data file remains intact.

The sequence diagram shows an add with an optional remark and label. It also shows that a failed save leaves the live model unchanged. Invalid parameters or a duplicate Student ID stop execution before saving.

Startup and feedback

MainApp starts empty when the data file is missing. If loading fails, it creates an empty model and configures LogicManager to block modifying commands until the file is fixed and the application is restarted. The error is Student data is unavailable because loading failed. Fix the data file and restart. This prevents an empty model from overwriting unreadable or invalid records. Read-only commands remain available.

Successful adds display Added student ID: NAME., followed by Remark: TEXT when the remark is non-empty, and the total student count on the next line. The count uses the complete record list. PersonCard displays labels and non-empty remarks with wrapping, and hides the remark field for empty remarks. JSON storage preserves remarks and defaults missing/null remark fields to empty strings.

Verification

Tests cover field boundaries and normalisation, label parsing, parameter errors and ordering, duplicate IDs with changed details, feedback with/without remarks, JSON round trips, filtered index handling, startup loading failures, and save failures. Replacement-failure tests simulate an error after the temporary file is written and check that the original file, records, and active filter remain unchanged. They also check temporary-file cleanup and failed first saves.

Find command

Command format: find n/KEYWORD [MORE_KEYWORDS]..., find i/KEYWORD [MORE_KEYWORDS]..., find e/KEYWORD [MORE_KEYWORDS]..., find r/KEYWORD [MORE_KEYWORDS]..., or find l/LABEL_NAME. Supply exactly one search field. Label searches replace the former standalone filter command. See the User Guide for examples and errors.

Validation and matching

  • ArgumentTokenizer recognises n/, i/, e/, r/, and l/.
  • FindCommandParser checks words before the first prefix, unknown prefixes, repeated prefixes, missing prefixes, multiple search-field types, empty values, and then label validity, in that order.
  • Name, ID, email, and remark values are split into whitespace-separated keywords. NameContainsKeywordsPredicate, StudentIdContainsKeywordsPredicate, EmailContainsKeywordsPredicate, and RemarkContainsKeywordsPredicate match any keyword using StringUtil#containsIgnoreCase, including partial matches.
  • RemarkContainsKeywordsPredicate searches Person#getRemark().value only. Empty remarks do not match non-empty keywords. Numeric slash text such as 8/10 is accepted under the existing prefix rules.
  • A label value is kept whole, validated by ParserUtil#parseLabel, and passed to LabelMatchesPredicate. This predicate lowercases both the requested and stored label names with Locale.ROOT, then compares the complete values, using the same rule as EditCommand and JsonAdaptedPerson. Internal spaces are preserved. This also handles Unicode lowercase expansions, such as İ becoming i followed by a combining dot, while keeping I and the dotless ı distinct.

For example, find n/alex david finds names containing either keyword, while find l/Discrete Math Tutorial finds students with that complete group label. find l/Tutorial does not match Discrete Math Tutorial. find r/recursion loops searches remarks for either keyword, and find r/curs also matches recursion. Empty r/, repeated r/, and combinations such as find r/recursion l/Tutorial 1 are rejected before execution.

Execution, persistence, and startup behaviour

AddressBookParser → FindCommandParser → FindCommand
FindCommand → Model#updateFilteredPersonList

Every search replaces the active predicate and evaluates the complete student list; searches do not narrow the previous result set. FindCommand returns the standard N person(s) listed! feedback. Zero matches clear the view. list restores all students. Invalid commands preserve the previous view.

FindCommand remains read-only. LogicManager executes it without saving, including when startup data loading failed. Student records and the saved JSON file remain unchanged.

Tests in RemarkContainsKeywordsPredicateTest, FindCommandParserTest, and FindCommandTest cover remark matching, invalid remark search inputs, result counts, and searching students hidden by a previous filter.

Deleting student information

Command format: delete i/STUDENT_ID. The display index is not used to identify students for deletion.

DeleteCommandParser accepts exactly one non-empty i/. It rejects line breaks, unknown prefixes, preamble text, repeated IDs, missing IDs, and empty IDs before calling ParserUtil#parseStudentId. ArgumentTokenizer#findUnknownPrefix shares the same case-sensitive alphabetic-prefix detection with add. An invalid Student ID retains the field constraint message instead of being replaced with a usage error.

DeleteCommand stores the validated StudentId and searches model.getAddressBook().getPersonList() for an exact normalised ID match. It retrieves the existing Person and passes that object to model.deletePerson. This removes the entire record, including remarks and labels, without separately deleting its fields. The complete record list is searched so a student hidden by a filter can still be deleted.

For example, after find n/Benson, delete i/a1234567b removes Alice's A1234567B record while the displayed Benson results remain unchanged. If Alice is already absent, the command reports Student with ID A1234567B is not in the records. and changes no data. Successful feedback is Deleted student A1234567B: Alice Pauline.

Deletion preserves the current filter and returns true from Command#isModifyingData. LogicManager therefore performs it on the temporary model, saves the proposed records, and only then publishes the change. If saving fails, the live record, filter, and previous saved file remain unchanged. If startup loading failed, deletion is blocked by the existing loading guard.

Loading student data at startup

The startup messages and the commands available after a failed load are documented in the User Guide.

Loading and error reporting

The loading path is:

MainApp#initModelManager → StorageManager → JsonAddressBookStorage → JsonSerializableAddressBook
MainApp#initLogic → LogicManager
  1. JsonAddressBookStorage#readAddressBook returns Optional.empty() if the data file does not exist.
  2. If the file exists, JsonUtil#readJsonFile reads it. Failures are reported as DataLoadingException with one of two messages, chosen by the cause:
    • an IOException other than a JSON error, such as missing read permission, gives Unable to load student data.
    • a JsonProcessingException, such as malformed JSON, gives Unable to load student data. The data file may be corrupted or invalid.
  3. JsonSerializableAddressBook#toModelType converts records in file order. A missing or invalid field throws IllegalValueException, which is reported with the corrupted or invalid message. A repeated Student ID throws DuplicateStudentIdException, a subclass of IllegalValueException. JsonAddressBookStorage catches it first so that its specific message, Unable to load student data: duplicate Student ID A0123456B detected., is kept. Student IDs are compared after normalisation to uppercase.
  4. MainApp records the outcome as the startup message: N students loaded. (1 student loaded. for one record), the no-existing-data message, or the DataLoadingException message.
  5. MainWindow#fillInnerParts shows Logic#getStartupMessage in the result display when the window opens.

The sequence diagram below shows the loading path. The alt block shows the three outcomes of reading the data file: a successful load, a missing file, and a DataLoadingException. Model and logic creation continue the same way after each outcome.

Blocking modifications after a failed load

When loading fails, MainApp starts with an empty AddressBook and passes isStudentDataAvailable = false to LogicManager. LogicManager#execute parses each command first, so malformed commands still receive their usual error messages. It then rejects any command whose Command#isModifyingData returns true with Student data is unavailable because loading failed. Fix the data file and restart.

This prevents the empty in-memory list from being saved over the user's data file, which may still be recoverable. Read-only commands, such as list and find, still run against the empty list. Restarting is the only way to retry loading.

Saving is described in Saving before publishing changes.

Design considerations

Aspect: What to do when the data file cannot be loaded

  • Alternative 1 (current choice): Start with an empty list, keep the file, and block modifying commands.
    • Pros: The user's data file is never overwritten, and the user sees why loading failed.
    • Cons: The app cannot be used to change records until the file is fixed.
  • Alternative 2: Start with an empty list and allow modifying commands, as in AddressBook-Level3.
    • Pros: The app remains fully usable.
    • Cons: The first save overwrites the original file, losing data that might have been fixable.

Verification

MainAppTest covers a missing file, files with zero, one, and several students, a corrupted file, and duplicate Student IDs. It checks that modifying commands are blocked and the file is unchanged after a failed load. JsonAddressBookStorageTest covers unreadable files, invalid JSON, invalid values, and duplicate Student IDs.

Undoing data changes

LogicManager owns an in-memory deque of complete AddressBook snapshots. It retains at most 100 prior states. The snapshots contain student data only; GUI settings and the current find or filter predicate are not recorded. History begins empty on every application start and is never written to JSON.

Before a normal data-changing command runs, LogicManager copies the live address book. It executes the command on the existing pending model and saves that proposed address book. Only after the save succeeds does it append the pre-change snapshot, discarding the oldest snapshot first when the deque is full, and publish the pending model. Thus parsing, validation, execution, or save failures leave the live records and undo history unchanged.

For undo, LogicManager examines the newest snapshot without removing it. It saves that snapshot before replacing the live address book, resets the displayed list with Model.PREDICATE_SHOW_ALL_PERSONS, and then removes the snapshot. (The displayed list is reset to default, as it could be stale after an undo, for example with a filter applied. The current design also does not support the notion of saving a "filter", implying "updating the filter" being out-of-scope, hence the decision to reset the displayed list.) If saving fails, live records, the displayed list, the saved file, and history remain unchanged. If no snapshot exists, it returns Nothing to undo. without saving.

Undo is destructive: restoring a snapshot discards the state being reversed, so there is no redo or forward branch. A later successful data change records the then-current state as a new predecessor.

Design consideration

Aspect: How undo stores prior state:

  • Current choice: Complete address-book snapshots in LogicManager.
    • Pros: One transaction handles every data-changing command and keeps saving before publishing explicit.
    • Cons: Each retained state copies the address-book list structure.
  • Alternative: Command-specific inverse operations.
    • Pros: Can retain less state for some commands.
    • Cons: Every data-changing command must implement and validate its own reverse operation.

Appendix: Requirements

Product scope

Target user profile:

TeachAssist is for teaching assistants (TAs) who support a fixed group of undergraduate students through weekly tutorials and consultations throughout a semester. They need to retrieve and update student information quickly while handling teaching, assessment, and follow-up tasks.

Value proposition: Help teaching assistants organise student information and learning progress so they can remember individual students' needs and provide consistent, targeted support throughout the semester.

TeachAssist supports the management of student information, learning progress, interactions, and follow-up needs. It does not aim to replace a learning management system (LMS) for distributing teaching materials, conducting assessments, calculating official grades, or communicating directly with students.

Use cases

(For all use cases below, the System is the TeachAssist and the Actor is the Teaching Assistant, unless specified otherwise)

Use case: UC01 - Add a Student MSS:

  1. TA enters command to add a student with name, student ID, email, and optional remarks and group label.
  2. TeachAssist validates the student details and checks for duplicate student IDs.
  3. TeachAssist saves the student record to the data file.
  4. TeachAssist displays a confirmation message and updates the student list. Use case ends.

Extensions

  • 1a. The command format is invalid or required parameters are missing or empty.
  • 1a1. TeachAssist shows an error message naming the missing/empty parameter or explaining the invalid format.
  • Use case ends.
  • 1b. An unknown or repeated parameter is supplied.
  • 1b1. TeachAssist shows an error message naming the offending prefix. No student data changes.
  • Use case ends.
  • 1c. The student data file failed to load at startup.
  • 1c1. TeachAssist blocks the add command and asks the TA to fix the data file and restart.
  • Use case ends.
  • 2a. One or more field values are invalid (e.g., malformed student ID, invalid email format, or invalid name characters).
  • 2a1. TeachAssist shows an error message indicating the invalid field value.
  • Use case ends.
  • 2b. A student with the given student ID already exists in TeachAssist.
  • 2b1. TeachAssist shows an error message indicating that the student ID already exists.
  • Use case ends.
  • 3a. Saving data to the file fails.
  • 3a1. TeachAssist shows an error message indicating that it is unable to save student data.
  • 3a2. TeachAssist leaves existing student records, the displayed filter, and the previous saved file unchanged.
  • Use case ends.

Use case: UC02 - Find a Student MSS:

  1. TA enters a search command specifying a name, student ID, email, remark, or label query.
  2. TeachAssist searches existing records for matches.
  3. TeachAssist displays the list of matching student records and the count of results. Use case ends.

Extensions

  • 1a. The command contains no search parameters, multiple search parameters, or empty query fields.
  • 1a1. TeachAssist shows an error message explaining the correct find format.
  • Use case ends.
  • 1b. The search query contains invalid characters.
  • 1b1. TeachAssist shows an error message indicating invalid characters in the query.
  • Use case ends.
  • 2a. No student records match the search query.
  • 2a1. TeachAssist displays a message indicating no matching students were found.
  • 2a2. TeachAssist clears the displayed student list.
  • Use case ends.

Use case: UC04 - Find Students by Group Label MSS:

  1. TA enters find l/LABEL_NAME to find students by a specific complete group label.
  2. TeachAssist scans stored records for matching group labels.
  3. TeachAssist displays only the students belonging to that group label. Use case ends.

Extensions

  • 1a. The group label parameter is missing or empty.
  • 1a1. TeachAssist shows an error message indicating the missing or empty parameter.
  • Use case ends.
  • 1b. Multiple label parameters are provided.
  • 1b1. TeachAssist shows an error message indicating that the parameter must be specified only once.
  • Use case ends.
  • 2a. No students have the specified group label.
  • 2a1. TeachAssist displays a message indicating no students were found with that label.
  • 2a2. TeachAssist clears the displayed student list.
  • Use case ends.

Use case: UC05 - Delete a Student MSS:

  1. TA enters command to delete a student using their student ID.
  2. TeachAssist verifies that the student exists in the records.
  3. TeachAssist removes the student record and saves the changes to the data file.
  4. TeachAssist displays a confirmation message and updates the student list. Use case ends.

Extensions

  • 1a. The student ID parameter is missing, empty, or improperly formatted.
  • 1a1. TeachAssist shows an error message specifying the invalid parameter or usage format.
  • Use case ends.
  • 1b. The command contains a repeated Student ID or an unknown parameter.
  • 1b1. TeachAssist shows the error message naming the offending prefix without changing student records.
  • Use case ends.
  • 1c. The data file failed to load at startup.
  • 1c1. TeachAssist blocks deletion and asks the TA to fix the data file and restart.
  • Use case ends.
  • 2a. No student with the specified student ID exists in the records.
  • 2a1. TeachAssist shows an error message stating that the student is not in the records.
  • Use case ends.
  • 3a. Saving data to the file fails.
  • 3a1. TeachAssist shows an error message indicating that it is unable to save student data.
  • 3a2. TeachAssist retains the entire student record, current filter, and previous saved file.
  • Use case ends.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should be able to hold up to 1000 persons without noticeable sluggishness in performance for typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
